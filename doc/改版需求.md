# axum78 改版需求

## 一、背景与目标

`axum78` 是基于 `axum` 0.7 的 Web API 框架，参考 `koa78-base78`，实现了 4 级路由、统一请求/响应、CRUD 基类。当前是**常驻 TCP 监听的传统服务器**，依赖 `tokio`、`TcpListener`、`rusqlite`、`mysql`、`memcache` 等，**无法部署到 Cloudflare Workers**。

**核心诉求：一套业务代码，同时覆盖国内 + 海外部署。**

- **海外**：编译 wasm，用 `workers-rs` 部署到 Cloudflare Workers。
- **国内**：编译普通 x86_64 二进制，用 `axum` 部署到自建服务器（如阿里云 99 元 2H2G）。

技术栈已定 **Rust**，存储需求为**持久化存储**（关系型）。

## 二、关键约束（决策依据）

1. **国内直连 CF 不稳定**：CF 免费/付费边缘节点国内延迟高、间歇不可达，`workers.dev` 基本打不开；CF 中国网络仅企业版才有。所以国内必须保留自建服务器入口。
2. **CF Workers 运行时模型**：无状态、无常驻进程、无 TCP 监听、无本地文件、CPU 受限。`tokio`、`std::net`、`std::fs`、`reqwest blocking`、原生数据库驱动在 wasm32 下**无法编译/运行**。
3. **存储需可替换**：CF 侧用 **D1**（SQLite 兼容），国内侧用 **SQLite**（`rusqlite`），用 trait 统一。
4. **账号**：1 个 CF Paid 账号（$5/月）足够（1000 万请求/月、最长 5 分钟 CPU/请求）。

## 三、现状（不兼容点）

| 依赖/能力 | 用途 | wasm32 下 |
|-----------|------|-----------|
| `tokio` (full) | 异步运行时 | ❌ |
| `std::net::TcpListener` | 监听端口 | ❌ |
| `axum::serve` | 启动服务 | ❌（换 fetch handler） |
| `rusqlite` (bundled) | 本地 SQLite | ❌（换 D1） |
| `mysql` 25 | 直连 MySQL | ❌（换 Hyperdrive/D1） |
| `memcache` | 直连缓存 | ❌（换 KV） |
| `reqwest` (blocking) | 同步 HTTP | ❌（换 fetch） |
| `std::fs` | 本地文件 | ❌（换 R2） |

**可复用**（应抽到核心库）：4 级路由匹配与安全校验、`UpInfo`/`RequestBody`/`ApiResponse` 数据结构、`BaseApi` 的 CRUD 逻辑、各业务控制器。

## 四、目标架构

**可移植库 + 双薄壳入口 + 存储 trait 抽象**：

```
                 ┌─ 海外入口（workers-rs，wasm）──→ CF Workers ── D1
可移植业务核心库 ─┤
                 └─ 国内入口（axum + tokio）────→ 自建服务器 ── SQLite
```

### 分层职责

1. **核心库（core）**：纯 Rust，无 `tokio`/`std::net`/`std::fs`/原生 DB，能 `cargo check --target wasm32-unknown-unknown` 通过。含路由匹配（纯函数）、安全校验、数据结构、`BaseApi` CRUD、业务控制器、`trait Storage` 定义。
2. **海外入口（worker-cf）**：`workers-rs` + `#[event(fetch)]`，解析 URL 提取 4 级路由 → 调核心库 → 返回 `ApiResponse`；实现 `D1Storage`。
3. **国内入口（server-cn）**：`axum` + `tokio`，复用现有 `server.rs` 写法；实现 `SqliteStorage`。

### 存储抽象

```rust
#[async_trait]
pub trait Storage: Send + Sync {
    async fn query(&self, sql: &str, params: &[Value]) -> Result<Vec<Row>, Error>;
    async fn execute(&self, sql: &str, params: &[Value]) -> Result<usize, Error>; // 影响行数
}
```

- CF 侧 `D1Storage`：SQL 翻译为 D1 HTTP 调用。
- 国内侧 `SqliteStorage`：走 `rusqlite` / `datastate::Sqlite78`。

### 目录规划

```
rust-workers-template/
├── Cargo.toml              # workspace
├── core/                   # 可移植核心库
│   └── src/{lib,router,context,response,base_api,storage}.rs + controllers/
├── worker-cf/              # 海外入口（workers-rs + wrangler.toml + D1Storage）
├── server-cn/              # 国内入口（axum + SqliteStorage）
└── deploy/{deploy-cf.sh, deploy-cn.sh}
```

### 关键设计点

1. 路由「路径 → 控制器」查找改成**纯函数**，`Method` 换成自定义 `HttpMethod` 枚举，核心库不依赖 axum。
2. `BaseApi` 的 `do_get`/`do_m_add`/`do_m` 全部改为通过 `trait Storage` 调用。
3. 如需外部 HTTP，定义 `trait HttpClient` 抽象（CF 用 `Fetch`，国内用 `reqwest` async）。

### 存储对照

| 能力 | CF 侧 | 国内侧 |
|------|-------|--------|
| 关系型 | D1 | SQLite |
| 键值 | KV | Redis/内存 |
| 对象 | R2 | 本地磁盘 |
| MySQL 兼容 | Hyperdrive（可选） | MySQL 直连 |

## 五、迁移步骤

**阶段 0 准备**：现有代码 `cargo build`/`cargo test` 通过；建 workspace；装 `wasm32-unknown-unknown` 目标。

**阶段 1 抽核心库**：迁移 response/context → 改造 router 为纯函数 → 定义 `trait Storage` → 改造 `BaseApi` 走 Storage → 迁移业务控制器；每步保证 wasm32 编译通过。

**阶段 2 海外入口**：`worker-cf` 实现 `#[event(fetch)]` + `D1Storage` + `wrangler.toml`；`wrangler dev` 验证；`wrangler deploy`。

**阶段 3 国内入口**：`server-cn` 实现 axum 薄壳 + `SqliteStorage` + 复用 `sid_auth_middleware`；编译 x86_64 验证。

**阶段 4 示例应用**：一个 CRUD 示例，业务逻辑在核心库走 Storage；D1 / SQLite 各建一次表（同一份 SQL），验证双端一致。

**阶段 5 部署与文档**：`deploy-cf.sh`、`deploy-cn.sh`、systemd 模板、README。

## 六、验收标准

1. 一套核心库业务代码不改，海外 CF / 国内 axum 均正确响应同一接口。
2. 切换 D1 / SQLite 仅改入口侧 `Storage` 实现，业务逻辑零改动。
3. 核心库 `cargo check --target wasm32-unknown-unknown` 无错误。
4. 示例应用双端均能完成 CRUD。

## 七、风险与应对

| 风险 | 应对 |
|------|------|
| 核心库残留框架/运行时依赖 | 每阶段末做 wasm32 编译检查 |
| D1 与 SQLite 语法差异 | 用两者兼容的 SQL 子集，差异封装进 `Storage` 实现 |
| 异步 trait 在 wasm 兼容性 | 必要时用 `wasm-bindgen-futures` |
| 鉴权（sid）依赖 DB | 鉴权数据访问也走 `trait Storage` |
| 现有 MySQL/memcached 能力 | 首期 CF 侧不实现，国内侧保留 |
